Weights, caches
and guesses

To write one token, a language model reads every one of its weights and every key and value of the conversation so far — gigabytes moved to produce a few bytes. This guide follows that one fact through model architecture, the KV cache and how it is paged, compressed and offloaded, and the speculative tricks that turn one expensive read into several tokens.

Origins

Who built this, and what for

Where did each idea in modern inference come from?

The serving stack was assembled in about eight years, mostly by people trying to fit more conversations onto the same GPU. Read in order, the dates show the problem moving: first compute, then memory, then the bandwidth between them.

2017The TransformerVaswani et al., GoogleAttention over every earlier token, generated one token at a time. Caching each token’s keys and values — the KV cache — follows immediately, and so does most of this guide.
2019Multi-query attentionNoam Shazeer, Google“One write-head is all you need”: share one K and V across all heads. Decoding got much faster; quality dropped a little. The first time anyone designed attention around memory bandwidth.
2021RoPESu et al. · RoFormerPosition encoded as a rotation of queries and keys. Now nearly universal — and the reason a cached key belongs to one position.
2022FlashAttentionTri Dao et al., StanfordAttention computed in tiles that never write the full score matrix to memory. Faster, and the reason score-based eviction is hard (11).
2022OrcaYu et al. · OSDI ’22Schedule every iteration, not every request. Continuous batching is now the default in every serving engine.
2023GPTQ · AWQFrantar et al. · Lin et al.4-bit weights without retraining, by correcting errors column by column or by protecting the channels that matter.
2023Speculative decodingLeviathan et al., Google · Chen et al., DeepMindTwo groups, the same idea, the same proof: draft cheaply, verify in one pass, and keep the target model’s exact output distribution.
2023Grouped-query attentionAinslie et al., GoogleThe middle ground between MHA and MQA — and a recipe to convert existing models. Adopted by almost every open model since.
2023PagedAttention · vLLMKwon et al., UC Berkeley · SOSP ’23The cache in fixed-size pages behind a block table. Waste fell from most of the cache to a few percent.
2023Attention sinks · H2OXiao et al., MIT · Zhang et al.Attention concentrates on a few tokens — some meaningful, some just the first ones. The start of cache eviction research.
2023Prompt lookup decodingApoorv SaxenaSpeculation with no draft model: find the last tokens earlier in the prompt and propose what followed. A few lines of code.
2024Medusa · EAGLECai et al. · Li et al.Drafters built into the target model as extra heads, trained in hours rather than as a separate model.
2024RadixAttention · SGLangZheng et al., LMSYSEvery cached prefix indexed in a radix tree and reused automatically across requests.
2024Multi-head latent attentionDeepSeek-AI · DeepSeek-V2Cache a compressed latent instead of keys and values. DeepSeek reported a 93% smaller cache than their previous 67B model.
2024KIVILiu et al. · ICML ’242-bit keys and values without training, by quantizing keys per channel and values per token.
2024DistServe · Splitwise · MooncakeZhong et al. · Patel et al. · Moonshot AIPrefill and decode on different machines, the cache shipped between them — and a KV store as the centre of the system.
2024Multi-token predictionDeepSeek-V3A model trained to predict its next two tokens, then used as its own draft model at inference.
The pattern worth noticing: almost nothing here made the model smarter. Every entry is about moving fewer bytes, wasting less memory, or doing two things in the time of one — which is why a model from 2023 can serve several times faster today on the same hardware.

Part I
The model

What the network is made of — blocks, attention variants and experts — at the level of detail that decides inference cost.

01 — One block, many times

The anatomy of a decoder

What is a language model made of, at the level that matters for inference?

A decoder-only language model is a stack of identical blocks between an embedding table and an output head. Almost everything about the cost of inference can be read off this one diagram: what is stored per token, what is read per step, and which parts are large matrix multiplies.

Counting parameters and FLOPs

Every weight in a block takes part in exactly one multiply and one add per token, so the forward pass costs about two FLOPs per parameter, plus an attention term that grows with how much context the token can see.

# Llama 3.1 8B · d = 4,096 · 32 query heads, 8 KV heads of 128 · FFN 14,336 · 32 layers
attention per layer   = d·d (Q) + 2 · d·(8·128) (K, V) + d·d (O)      = 41.9 M
MLP per layer         = 3 · d · 14,336  (gate, up, down)                = 176.2 M
32 layers                                                              = 6.98 B
embedding + LM head   = 2 · 128,256 · 4,096                             = 1.05 B
total                                                                  ≈ 8.03 B

FLOPs per token ≈ 2 · P  +  4 · layers · context · d
                ≈ 16 GFLOP        +  4.3 GFLOP at 8k context            # attention is ~20% here, more at longer context

The ratio to remember: a decode step reads every weight once and does two FLOPs with it. A GPU can do hundreds of FLOPs in the time it takes to read one byte. Section 04 is what follows from that mismatch, and most of the rest of the guide is ways around it.

02 — Attention and its variants

How many keys and values per token?

What do MHA, MQA, GQA and MLA actually change?

Attention is the only part of the block where tokens see each other, and the only part with state that grows as the conversation does. Each variant below is a different answer to one question: how many key and value vectors should be stored for every token?

VariantCached per token per layerAt 64 heads × 128vs MHASeen in
MHA2 · heads · head_dim16,384 values1×GPT-3, Llama 2 7B/13B
GQA · 8 groups2 · kv_heads · head_dim2,048 values8× smallerLlama 3, Qwen2.5, Mistral
MQA2 · head_dim256 values64× smallerPaLM, Falcon 7B
MLAlatent + one shared RoPE key512 + 64 = 576 values~28× smallerDeepSeek-V2, V3, R1

GQA won because it sits at the knee of the curve: most of MQA’s memory saving, almost none of its quality loss, and it can even be added to an existing MHA model by averaging heads and briefly retraining. MLA goes further but has to be designed in from the start.

How MLA gets away with it

MLA projects each token down to a 512-dimensional latent c and caches only that. At training time, per-head keys and values are up-projected from c. At inference the up-projection for keys is folded into the query projection, and the one for values into the output projection, so attention is computed directly against the cached latents. It costs more arithmetic per step in exchange for reading far fewer bytes — exactly the right trade for a phase that is bandwidth-bound (04).

RoPE, and why cached keys are position-bound

Rotary position embedding rotates each pair of dimensions in a query and key by an angle proportional to the token’s position, so the dot product between them depends only on their distance. Keys are cached after rotation, which means a cached entry is tied to the position it was computed at: a prefix can be reused at the same positions (08), but the same text at a different offset can’t simply be pasted in. MLA can’t fold rotation into its latent either, which is why it caches a separate 64-dimensional rotated key shared by all heads — the “+ 64” in the table.

03 — Mixture of experts

Not every parameter runs

Why can a 671B-parameter model cost like a 37B one — and when can’t it?

A mixture-of-experts layer replaces the single MLP with many smaller ones and a router that picks a few for each token. Total parameters decide how much memory the model needs; active parameters decide how much work each token does.

ModelTotal paramsActive per tokenRouted experts · activeShared
Mixtral 8×7B46.7 B12.9 B8 · 2—
Mixtral 8×22B141 B39 B8 · 2—
Qwen3-235B-A22B235 B22 B128 · 8—
DeepSeek-V3671 B37 B256 · 81
At batch size 1

Cheap like a small model

  • A decode step reads only the experts this token was routed to.
  • DeepSeek-V3 reads ~37 B parameters per token, not 671 B.
  • Memory still has to hold all of them.
At large batch

Every expert, every step

  • With hundreds of tokens in a step, almost every expert is picked by someone, so nearly all weights are read anyway.
  • Each expert then sees only a slice of the batch — small, inefficient matrix multiplies.
  • The fix is expert parallelism: spread experts over many GPUs so each sees a large batch of its own tokens (18).
For the KV cache, MoE changes nothing. Experts replace the MLP; attention is untouched. A MoE model’s cache is set by its attention design alone — which is why DeepSeek paired 256 experts with MLA.

Part II
Prefill and decode

The two phases of serving a request, why one is limited by arithmetic and the other by memory, and how batching bridges them.

04 — Two phases, two bottlenecks

Prefill computes, decode reads

Why is generating a token so much slower than reading one?

Serving a request has two phases that stress the GPU in opposite ways. Prefill reads the whole prompt in one pass and is limited by arithmetic. Decode writes one token at a time and is limited by how fast weights and cache can be read from memory.

Prefill

Many tokens, one pass

  • All prompt tokens go through every layer together, as large matrix multiplies.
  • Each weight read from memory is used for thousands of tokens.
  • Compute-bound. Writes the prompt’s K and V into the cache.
  • Sets time to first token.
Decode

One token, one pass

  • Each step produces one token per sequence and must read every weight again.
  • Each weight is used for one token per sequence in the batch.
  • Bandwidth-bound. Also reads every cached K and V for each sequence.
  • Sets inter-token latency.
# one forward step · P parameters · weights stored in 2 bytes (BF16)
FLOPs      ≈ 2 · P · tokens_in_step
bytes read ≈ 2 · P  +  KV bytes for every sequence in the step
arithmetic intensity = FLOPs ÷ bytes

prefill, 2,048-token prompt     ≈ 2,048 FLOPs/byte     # compute-bound
decode, batch 1                 ≈ 1 FLOP/byte          # bandwidth-bound
decode, batch 64                ≈ 64 FLOPs/byte        # before counting KV reads
H100 SXM ridge point            ≈ 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOPs/byte

The speed limit of one stream

At batch 1, a decode step can’t finish faster than the time to read the weights once. That gives a hard ceiling on tokens per second for a single user, before any engine overhead:

tokens/s per stream  ≤  memory bandwidth ÷ bytes of weights

Llama 3.1 8B  · BF16 · 1 × H100     3.35 TB/s ÷ 16 GB    ≈ 209 tokens/s
Llama 3.3 70B · FP8  · 2 × H100     6.70 TB/s ÷ 70.6 GB  ≈ 95 tokens/s

Batching amortises the weights, not the cache

A batch of 64 sequences reads the weights once per step but reads 64 separate KV caches. For Llama 3.1 8B at 8k tokens of context, that is 64 × 8,192 × 128 KiB = 64 GiB of cache per step against 16 GB of weights. At long context the cache, not the model, is most of what decode reads — which is why shrinking it (Part “Compression”) makes decode faster, not just smaller.

05 — Batching is the whole game

Throughput comes from the batch

How does one GPU serve hundreds of conversations at once?

A decode step costs about the same whether it advances one sequence or fifty, so throughput comes from batching. The art of a serving engine is keeping the batch full without letting any one sequence wait — and the limit on how full it can get is KV cache memory.

BatchBytes read per stepStep timeTokens/s per streamTokens/s total
116.3 GB4.9 ms205205

Llama 3.1 8B in BF16 on one H100, every sequence holding 2,048 tokens of context, step time taken as bytes ÷ 3.35 TB/s — an idealised roofline estimate; real engines land lower. Total throughput rises 47× while each user’s stream slows 4×. Batch 192 is close to the ceiling: 192 × 2,048 tokens of cache is 51 GB, about all that fits beside the weights.

Continuous batching

Early servers batched whole requests: start eight together, wait for the longest to finish, start the next eight. Short answers left their slot idle until the batch drained. Iteration-level scheduling (Orca) re-forms the batch on every step — a sequence joins as soon as there is room and leaves the moment it emits its end token — so slots are never idle while there is work waiting.

Chunked prefill

A new request has to be prefilled before it can join the decoding batch. Run as one large pass, a 32k-token prompt stalls every decoding stream on the GPU for the length of that pass. Chunked prefill (Sarathi-Serve) splits the prompt into pieces and mixes one piece into each step alongside the decode tokens, under a per-step token budget. Decode steps are bandwidth-bound and leave compute idle; prefill chunks fill exactly that idle compute.

# one engine step under a token budget of 2,048
step = [ 1 token × 190 decoding sequences ]           # 190 tokens · bandwidth-bound
     + [ next 1,858 tokens of a new 32k-token prompt ] # fills the idle compute

budget up   → new prompts finish prefill sooner (better time to first token)
budget down → each step is shorter (better inter-token latency for everyone else)
Where batch size runs out: the engine can only admit a sequence if its KV cache will fit. When it can’t, a running sequence is preempted — its cache dropped and recomputed later, or copied to host memory. Every technique in the next three parts raises that ceiling: store the cache more cleverly, store less of it, or store it somewhere else.

Part III
The KV cache

The state attention keeps for every token: how big it is, how it is laid out, and how a shared prefix is computed once.

06 — What the cache holds

Memory instead of recomputation

How big is the KV cache, and what decides it?

Without a cache, generating token n would recompute keys and values for all n − 1 earlier tokens in every layer, every step. With it, each token’s K and V are computed once and read on every later step. Compute is traded for memory — and the memory bill decides how many conversations fit on a GPU.

# bytes of KV cache, for one sequence
2 × layers × kv_heads × head_dim × bytes_per_value × tokens
  ↑ one K and one V

# MLA stores a latent instead of per-head K and V
layers × (latent_dim + rope_dim) × bytes_per_value × tokens
per token—
per sequence—
all sequences—
weights, for scale—

Try the 70B model at 32k tokens and 16 sequences: 160 GiB of cache, two H100s’ worth before a single weight is loaded. Switch to the MHA variant of the same size and it is eight times worse — the reason GQA became standard. Switch to DeepSeek-V3 and a model ten times larger needs a fraction of the cache.

07 — Pages, not slabs

PagedAttention

How is the cache laid out in GPU memory?

Nobody knows in advance how long an answer will be. Early servers reserved a contiguous slab of cache for each sequence sized to its maximum length, and most of that memory sat empty. PagedAttention borrowed the operating system’s answer: fixed-size pages, allocated as the sequence grows, found through a table.

Allocation

On demand

A new block is taken from the free list each time a sequence crosses a 16-token boundary. The vLLM paper measured earlier systems wasting 60–80% of cache memory to reservation and fragmentation; paging brings it under 4%.

Sharing

Copy on write

Parallel samples of one prompt, or beam-search branches, share their common blocks. Only when a branch writes into a shared, partly filled block is that block copied.

Pressure

Preempt by block

When the pool runs dry, a running sequence’s blocks are freed — either dropped and recomputed later, or copied to host memory and copied back (12).

Block size is a trade. Smaller blocks waste less memory and share prefixes more finely; larger blocks mean fewer table lookups and more efficient memory access in the attention kernel. Sixteen tokens is the common default.

08 — Reusing a prefix

Prefix caching

When can a request skip its own prefill?

Many requests start the same way — a system prompt, a block of few-shot examples, a shared document, the earlier turns of a conversation. If the K and V for that beginning are already in the cache, prefill for that part costs nothing.

vLLM · hash chain

Name a block by everything before it

  • A full block’s key is a hash of its parent block’s key and its own tokens, plus extras such as a LoRA adapter or a cache salt.
  • So a key identifies the whole prefix up to that block, not just 16 tokens.
  • Finished sequences’ blocks stay in the pool, marked evictable, until memory is needed — least recently used first.
SGLang · radix tree

Index every prefix ever seen

  • Cached tokens form a radix tree; each edge is a run of tokens with its KV.
  • A new request walks the tree as far as it matches, and prefills only the rest.
  • Eviction removes least recently used leaves first, so shared trunks survive longest.
# vLLM-style block keys · a request’s cached prefix is the longest run of keys found in the pool
key(block 0) = hash( ∅,          tokens[0:16],  extras )
key(block 1) = hash( key(block 0), tokens[16:32], extras )
key(block 2) = hash( key(block 1), tokens[32:48], extras )
…

Exact prefixes only

A cached block is valid only if every token before it is identical, because every key and value depends on everything the token could attend to. Change one token at position 40 and everything after it must be recomputed. The practical rule for anyone writing prompts: put what never changes first and what always changes last. A timestamp at the top of a system prompt silently disables caching for everything below it.

WorkloadWhat gets reusedWhat breaks it
multi-turn chatAll earlier turns, every new messageTruncating or summarising history changes the prefix

RAGInstructions, and documents that recur in the same positionRetrieved chunks in a different order each time
few-shot · evalsThe examples block, across thousands of questionsRandomly sampled examples per question
Sharing has a privacy edge. A cache hit makes the first token arrive faster, and that is observable. Across users who shouldn’t learn about each other’s prompts, salt the block keys per tenant so hits can only happen within one tenant — vLLM exposes this as cache_salt.

09 — Five ways to make it smaller

Every factor has a technique

Which parts of the cache can be compressed, and by whom?

Local and global layers

Recent open models mix two kinds of attention layer. Local layers attend only to a sliding window of recent tokens, so their cache stops growing at the window size. Global layers see everything. Gemma 3 uses five local layers with a 1,024-token window for every global one, so at long context roughly five-sixths of its layers keep a fixed-size cache. The model learns during training to route long-range information through the few global layers.

As an operator you hold two of the five levers. Heads, dimensions, layer sharing and trained windows come with the checkpoint. What you choose at serving time is the precision of the cache (10) and whether to drop tokens from it (11) — and only the first of those is routinely safe.

10 — Fewer bits

Quantizing the cache

How far can keys and values be quantized, and why differently?

Storing keys and values in fewer bits doubles or quadruples how many tokens fit, and — because decode reads the whole cache every step — speeds decode up too. The catch is that keys and values are distributed differently, and a good scheme quantizes them differently.

PrecisionBytes per valueTokens per GB · Llama 3.3 70BHow it’s doneStatus
BF1623,052As computeddefault
FP8 E4M316,104Per-tensor or per-head scales, calibrated or computed on the flyproduction · --kv-cache-dtype fp8
INT4½ + scales~11,000Group-wise scales; keys per channel, values per tokensome engines; quality-sensitive
2-bit¼ + scales~20,000KIVI-style, recent tokens kept at full precisionresearch

Recent tokens stay sharp

Low-bit schemes usually keep a small window of the most recent tokens in full precision and quantize them in groups as the window fills. Recent tokens tend to receive the most attention, and grouping lets per-channel key scales be computed over a block of tokens rather than one at a time.

The kernel has to cooperate

The saving only becomes speed if the attention kernel reads the compressed values and dequantizes them in registers, so the bytes that cross the memory bus are the small ones. FP8 caches are supported this way by the major engines on Hopper-class GPUs; sub-8-bit caches need specialised kernels and are where most of the remaining engineering is.

11 — Fewer tokens

Windows, sinks and eviction

Can the cache simply forget the tokens that don’t matter?

In practice each head puts most of its attention on a small fraction of the tokens it can see. If you could tell in advance which ones, you could keep only those. A family of methods tries to — and the reasons they remain rare in production are as instructive as the methods themselves.

StreamingLLM

Attention sinks

ObservationModels dump spare attention onto the very first tokens. Evict them and generation collapses, even though they carry little content.
PolicyKeep about four initial “sink” tokens plus a recent window. Fixed-size cache, stable output over effectively unbounded streams.
CostAnything between the sinks and the window is gone. It streams; it does not remember.
H2O

Heavy hitters

PolicyTrack each token’s accumulated attention; keep the top scorers plus recent tokens; evict the lowest as new tokens arrive.
CostNeeds attention scores, which fused kernels never write out. A token evicted early can’t come back when it becomes relevant later.
SnapKV · PyramidKV

Compress once, after prefill

PolicyThe last few prompt tokens usually hold the question; their attention picks which earlier positions each head keeps. PyramidKV gives lower layers bigger budgets than higher ones.
CostGood for long-document question answering; weak when the question changes mid-conversation, because the vote was cast for the first question.

Why production rarely evicts

1

No scores to rank by

FlashAttention-style kernels never materialise the attention matrix — that is their whole point. Getting scores back means a slower kernel or an approximation.

2

Ragged per-head caches

Each head and layer keeps different tokens, which breaks the uniform block layout that paging relies on (07).

3

Prefix caching stops working

A compressed cache depends on the query that compressed it, so it can’t be reused for the next request with the same prefix (08).

4

Retrieval tasks fail quietly

“Find the clause in this contract” is exactly the case where the needed token got little attention until the question arrived. Once evicted, it is gone.

So production systems take their token savings from windows the model was trained with (09), take their byte savings from quantization (10), and solve the rest by putting the cache somewhere bigger — the next part.

12 — Load or recompute

The memory hierarchy, priced

Is it faster to reload an evicted cache or to compute it again?

When a cache entry has to leave GPU memory there are two ways to get it back later: recompute it with another prefill, or park it somewhere cheaper and load it. It is tempting to assume recomputing is faster. For almost every model and every tier below, the arithmetic says otherwise.

Why the arithmetic isn’t the whole answer

Bandwidth is shared — the same PCIe link carries other GPUs’ traffic and the NVMe drive serves the whole node. A load has a latency before the first byte, which matters for short prefixes. And the transfer has to overlap with compute to be free: good implementations stream the cache in layer by layer, loading layer i + 1 while layer i runs. Done that way, a cache hit from host memory costs little more than a hit in HBM.

13 — A cache that outlives the GPU

Tiers, sharing and handoff

What changes when the cache can live outside GPU memory?

Once loading beats recomputing, the KV cache stops being scratch memory that dies with a request and becomes a tiered store — kept in host memory and on disk, shared between GPUs, and shipped between machines that specialise in different phases.

Overflow and reuse

Engines expose the cache to an external store at two moments: when a block is evicted from HBM it can be written out instead of dropped, and when a request arrives its prefix is looked up outside the GPU as well as inside. vLLM does this through its KV connector interface, with LMCache as a common backend; SGLang’s hierarchical cache spills from GPU to host to storage; NVIDIA Dynamo has a KV block manager; Moonshot’s Mooncake built its whole serving architecture around a distributed KV store. The effect is a prefix cache measured in terabytes rather than tens of gigabytes — the difference between “recent conversations hit” and “any conversation from today hits”.

Handoff: disaggregated prefill and decode

A burst of long prompts on a GPU that is also decoding stretches every stream’s inter-token latency, even with chunked prefill. Disaggregation runs the two phases on separate GPUs, each tuned for its phase, and moves the cache between them. The transfer is the cost:

14 — Guess, then check

Speculative decoding

How can a model emit several tokens per step without changing its output?

A decode step leaves most of the GPU’s arithmetic idle, and checking five tokens costs almost the same as generating one. Speculative decoding spends that idle arithmetic on checking guesses — and, done properly, produces exactly the same distribution of outputs as decoding normally.

Why the output doesn’t change

The verify pass gives the target model’s probability distribution p at every drafted position. Draft token x, proposed with draft probability q(x), is accepted with probability min(1, p(x) / q(x)). At the first rejection, a replacement is sampled from the leftover distribution max(0, p − q), normalised. Leviathan et al. and Chen et al. showed independently in 2023 that this makes every emitted token distributed exactly as if the target had sampled it alone. With greedy decoding it reduces to: accept while the draft matches the target’s top token.

Drafting more tokens only pays when acceptance is high: at α = 0.5 the fifth through eighth guesses add almost nothing but still cost verification work. The real speedup is this number divided by the cost of a round — one verify pass plus whatever the drafter costs.

A low-batch tool. Speculation spends idle compute. At large batch the verify pass multiplies an already compute-heavy step by k + 1 tokens per sequence and stops being free, so the gain shrinks and can turn negative. Engines typically shorten or disable speculation as the batch grows — it is a latency optimisation for lightly loaded GPUs, not a throughput one.

Trees instead of chains

A chain of k guesses is wasted after its first wrong token. Tree drafting proposes several alternatives at each position — the top two candidates for token 1, the top two continuations of each, and so on — and verifies the whole tree in one pass using an attention mask that lets each node see only its own ancestors. Medusa, EAGLE-2 and SpecInfer all draft trees; the accepted path is the longest branch that survives.

Learned drafters

Good everywhere, cost something

  • Steady acceptance on open-ended text.
  • Need training data close to the real traffic, and must be retrained per target model.
  • Use GPU memory and time on every step.
Lookup drafters

Free, and only sometimes right

  • No model, no training, no memory — a few microseconds of CPU.
  • Near-perfect when output repeats input, near-zero otherwise.
  • A wrong guess costs one wasted verify slot, so they are safe to leave on at low batch (16).

Prompt lookup decoding

How does copying from the prompt speed up generation?

A great deal of what a model writes is already in its context — the code it is editing, the document it is summarising, the field names it was given in a schema. Prompt lookup decoding drafts by finding the last few tokens earlier in the context and proposing whatever came after them. It needs no model and no training.

# one round of n-gram drafting
context = prompt + output
for n in max_n … min_n:                                  # try longer matches first
    key = last n tokens of context
    find the first earlier occurrence of key in context
    if found: draft = the k tokens after it; break
verify draft in one target pass                          # accept the matching prefix, plus one token

Word-sized tokens for readability, greedy decoding, up to four drafted tokens, keys of two tokens then one. Real tokenizers split more finely, which makes runs of copied tokens longer.

Works well

Output that copies input

  • Code edits and refactors: most of the file comes back unchanged.
  • Summaries and answers that quote their sources.
  • Structured output that repeats field names from a schema or an example.
  • Multi-turn chats that revise an earlier answer.
Does little

Output that is new

  • Open-ended writing and brainstorming.
  • Translation — the output tokens aren’t in the prompt.
  • Short answers, where there are few rounds to speed up.
  • High batch sizes, where verification stops being free (14).

17 — Fewer bits for weights

Weight quantization

What do FP8, INT4 and FP4 weights buy, and in which phase?

Weights are read in full on every decode step, so storing them in fewer bits speeds decode up almost in proportion — and frees memory for the cache. What limits it is quality, and whether the arithmetic can also run in the smaller format.

FormatBytes per weightArithmetic inHowLlama 3.3 70B weights
BF162BF16As trained141 GB
FP8 · W8A81FP8 tensor coresPer-channel weight scales, per-token activation scales; near-lossless on large models71 GB
INT8 · W8A81INT8SmoothQuant moves activation outliers into the weights first71 GB

Weight-only · W4A16

Fewer bytes, same FLOPs

  • Weights are unpacked to 16 bits inside the kernel; the multiply is still BF16.
  • Big win in decode at small batch, which is bandwidth-bound.
  • Little or no win in prefill or at large batch, which are compute-bound — unpacking can even cost time there.
Weights and activations · W8A8

Fewer bytes and cheaper FLOPs

  • Both operands in 8 bits; H100 FP8 tensor cores run at twice BF16’s rate.
  • Helps both phases: half the bytes in decode, double the arithmetic in prefill.
  • The usual default for serving on Hopper-class GPUs.

How 4-bit stays accurate

Rounding every weight to 16 levels independently loses too much. GPTQ quantizes one column at a time and adjusts the not-yet-quantized columns to cancel the error, using second-order information from a small calibration set. AWQ observes that about 1% of weight channels matter far more than the rest — the ones multiplied by large activations — and scales those channels up before quantizing so they keep more precision. Both need a few hundred calibration samples, and neither needs retraining.

Weights and cache are separate decisions. An FP8 model can keep a BF16 cache and a BF16 model can use an FP8 cache. Quantizing weights frees memory once; quantizing the cache frees it per token, which is what matters at long context and high batch.

18 — Splitting a model

Tensor, pipeline, expert, data

How is a model cut across GPUs, and what happens to its cache?

When a model doesn’t fit on one GPU — or when one GPU’s bandwidth is too slow for it — it gets split. There are four ways to cut, each with its own communication cost and its own consequences for the KV cache.

SplitCommunicationWhat happens to the KV cacheUse when
tensor · TP2 all-reduces per layerKV heads divided across GPUs — each holds 1/TP of every token’s cacheWithin a node, to fit the model and cut step time
pipeline · PPactivations between stagesEach stage holds the cache for its own layersAcross nodes, when TP alone can’t fit the model
expert · EP2 all-to-alls per MoE layerUnaffected — attention isn’t split by expertsLarge MoE models, so each expert sees a big batch
data · DPnone between replicasEach replica keeps its own cache for its own requestsThe model fits; you need more throughput

Where tensor parallelism wastes cache

TP splits attention by KV head. Llama 3.3 70B has 8 KV heads, so TP up to 8 gives each GPU whole heads. At TP = 16 there aren’t enough heads to go round, each head is replicated on two GPUs, and the cluster stores every token’s cache twice. MLA is the extreme case: one latent per token that every head needs, so TP would replicate it on every GPU. That is why DeepSeek-V3 deployments typically run attention data-parallel — each GPU caches only its own requests — while the experts are spread with EP.

Reference

Glossary

Every term the guide leans on more than once. Each also appears as a dotted underline at its first use in a section — hover it there instead of coming here.

arithmetic intensity
FLOPs performed per byte moved from memory. Below the GPU’s ridge point a kernel is bandwidth-bound; above it, compute-bound.
attention sink
The first few tokens, which receive large amounts of attention regardless of content. Evicting them destabilises generation.
block table
A per-sequence list mapping its logical KV blocks to physical blocks in the pool, as a page table does for virtual memory.
chunked prefill
Splitting a prompt’s prefill into pieces mixed into decode steps, so long prompts don’t stall other streams.
continuous batching
Re-forming the batch every step: sequences join when there is room and leave when they finish.
decode
Generating one token per step. Reads every weight and the whole KV cache; bandwidth-bound.
expert parallelism
Spreading a MoE layer’s experts across GPUs and exchanging tokens with all-to-all, so each expert sees a large batch.
GQA
Grouped-query attention: groups of query heads share one key and value head. 8 KV heads for 64 query heads in Llama 3 70B.
inter-token latency
The time between successive generated tokens of one stream — one decode step.
KV cache
The keys and values of every earlier token, per layer, kept in memory so each decode step doesn’t recompute them.
MLA
Multi-head latent attention: cache one compressed latent per token and reconstruct per-head keys and values from it.
MoE
Mixture of experts: many MLPs per layer, of which a router picks a few for each token.
MQA
Multi-query attention: all query heads share a single key and value head.
PagedAttention
Storing the KV cache in fixed-size blocks found through a block table, so memory isn’t reserved or fragmented.
prefill
Processing the whole prompt in one pass to fill the KV cache. Compute-bound; sets time to first token.
prefix caching
Keeping KV blocks after a request ends, so a later request with an identical prefix skips that part of its prefill.
prompt lookup
N-gram speculation: draft by finding the last few tokens earlier in the context and proposing what followed them.
roofline
A plot of achievable performance against arithmetic intensity: a bandwidth slope up to the ridge point, then a flat compute roof.
RoPE
Rotary position embedding: rotate query and key dimensions by position-dependent angles so their dot product depends on distance.
speculative decoding
Draft several tokens cheaply, verify them in one target forward pass, keep the accepted prefix. Output distribution unchanged.
tensor parallelism
Splitting every layer’s heads and FFN columns across GPUs, with all-reduces after attention and the MLP.
time to first token
From request arrival to the first generated token: queueing plus prefill.
W4A16
4-bit weights unpacked to 16 bits for 16-bit arithmetic. Saves bytes, not FLOPs.
