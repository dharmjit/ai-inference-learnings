Origins

Who built this, and what for

Why does an inference API look the way it does?

The serving stack was assembled in about eight years, mostly by people trying to fit more conversations onto the same GPU. The trust model around it — one bearer key per caller — was borrowed from web APIs, and has barely changed since.

2017The TransformerVaswani et al., Google · “Attention Is All You Need”Generating one token at a time means every step re-reads the keys and values of every earlier token. Caching them — the KV cache — is where most of the rest of this guide spends its memory.
2018TensorRT Inference Server → TritonNVIDIADynamic batching: hold requests for a few milliseconds and run them together. It batches requests, which works for a classifier and badly for a stream whose length nobody knows.
2018Token scanningGitHubProviders register the shape of their secrets; GitHub reports matches pushed to public repositories. The single most useful thing a key format can do is be recognisable.
2020The GPT-3 APIOpenAIA model behind a bearer key, priced per token. Every inference API since has inherited the shape — including the fact that the key is the whole perimeter.
2021Prefixed, checksummed tokensGitHub · ghp_…A prefix that names the issuer and a checksum that lets anyone reject a typo offline. Section 06 copies both.
2022OrcaYu et al., Seoul National University · OSDI ’22Schedule per iteration, not per request: a sequence joins the batch when it arrives and leaves when it finishes. Continuous batching is now the default everywhere.
2022FlashAttentionTri Dao et al., StanfordAttention rewritten around memory traffic rather than arithmetic. The first loud signal that inference is bandwidth-bound.
2023Chat Completions over SSEOpenAIPOST /v1/chat/completions with stream: true became the de facto wire protocol — which is why this guide assumes it rather than designing one.
2023PagedAttention · vLLMKwon et al., UC Berkeley · SOSP ’23Allocate the KV cache in fixed-size blocks, like virtual memory pages. Fragmentation went away, and serving throughput for the same GPU went up severalfold.
2023Speculative decodingLeviathan et al., Google · Chen et al., DeepMindLet a small model guess several tokens and have the large one check them in one pass. Same output distribution, fewer expensive steps.
2024RadixAttention · SGLangZheng et al., LMSYSKeep KV blocks after a request finishes and index them by prefix, so the next request with the same system prompt skips its prefill. Useful, and — across tenants — a side channel.
2024Virtual Token CounterSheng et al. · OSDI ’24 · “Fairness in Serving LLMs”Fairness measured in tokens served, not requests. The first scheduler designed for the question in Part IV: who gets the next slot in the batch?
2024DistServe · SplitwiseZhong et al., OSDI ’24 · Patel et al., Microsoft, ISCA ’24Prefill and decode want different hardware balances, so run them on different GPUs and ship the KV cache between them.
2025Inference Gateway · llm-d · DynamoKubernetes SIG Network · Red Hat, Google, IBM et al. · NVIDIARouting that reads the engine’s queue and cache instead of counting connections. Load balancing finally learned what it was balancing.
The pattern worth noticing: nearly all of the invention is below the API — batching, paging, caching, routing. Above it, the design is a 2020 web API that nobody revisited: a bearer key and an HTTP endpoint. Shared, public, multi-tenant service is exactly where that inheritance stops being enough, and it is where this guide spends the gateway, key service and engine.

01 — The shape of it

Seven checks before a GPU sees a token

What happens between POST and the first token?

The service has one door. Everything that makes it safe to share — the key check, the limits, the routing — happens in a stateless gateway that stays on the connection until the last token has been sent.

0A per-IP limiter runs before authentication, so the auth path itself can’t be used to exhaust the gateway.
1The key’s prefix and checksum are checked offline. Random strings are rejected without touching a cache or a database.
2The key is looked up in the gateway’s own memory and its HMAC compared. The key service is off the path (07).

02 — The latency budget

Five milliseconds, spent in advance

How much can the service add before the GPU even starts?

Users feel two numbers: time to first token, and the gap between tokens after that. The gateway can only make the first one worse, so it gets a fixed budget and nothing on its path is allowed to wait on the network.

On the path

Memory, arithmetic, one hop

  • Key cache, token buckets, engine metrics — all local.
  • Every remote dependency is refreshed in the background and has a defined stale behaviour.
  • The only synchronous remote call is the replica itself.
Deliberately off it

Anything that can be slow

  • No database read to check a key; no call to the limit service per request.
  • No synchronous access log — logs are buffered and shipped.
  • Limit shares are rebalanced in the background, once a second (09).

Gateway

Stateless, on the connection for the whole stream, and the only door. Every per-request decision in the service is made here, from memory.

04 — The gateway holds on

The gateway stays for the whole conversation

Why doesn’t the gateway hand the request to a replica and step aside?

A web gateway’s work is done once the response starts. Here the response is the expensive part — it can run for minutes, and every token of it is GPU time shared with everyone else.

Step aside · L4 pass-through

Cheap, and blind

  • Gateway authenticates, then splices the client straight to a replica.
  • Fewer bytes through the gateway; no per-token work.
  • Cannot stop a stream part-way — for a revoked key, an output limit, or a drain — without teaching the replica about tenants.
  • Client disconnects become the replica’s problem, observed late or not at all.
Stay on the path · L7 proxy

Expensive, and in control

  • Gateway proxies every SSE event from the replica to the client.
  • Counts tokens as they pass, enforces output-token limits, and can end the stream cleanly.
  • Sees the client go away the moment it happens, and aborts the engine request.
  • Replicas know nothing about keys or tenants beyond a signed context.

This is the choice that makes mid-stream enforcement possible at all — revocation, output limits, clean shutdown — and it keeps the engine a pure compute service. The cost is that the gateway holds long-lived connections. It stops being sized by requests per second and starts being sized by concurrent streams — which Little’s law gives directly: 1,500 new streams a second that last 12 seconds on average is 18,000 open at once (03).

What goes over the wire

Server-sent events: a long HTTP response of data: lines, each a JSON delta. The service adds two things the minimal protocol leaves out — a comment line every 15 seconds so idle proxies don’t cut a slow stream, and a typed error event for the case where the stream has to stop early.

# a normal stream

A disconnect is an abort

When the client closes the connection — or an HTTP/2 client resets the stream — the gateway cancels its upstream request, and the engine frees that sequence’s KV blocks on its next step. Without this, a user who presses stop and retries twice costs three full generations, and the replica spends its memory on answers nobody will read.

Tokenize once, at the edge

The gateway applies the model’s chat template and tokenizes, then sends token IDs to the engine rather than text. The engine skips its own tokenization, and the gateway knows the exact input token count before admission — which token-denominated limits depend on (09). The tokenizer and template are versioned with the model: they ship in the same catalog release as the weights, and the gateway refuses to route to a replica whose model revision doesn’t match its own.

Deploying a gateway without cutting streams

A gateway pod being replaced stops accepting new connections, then keeps its existing streams until they finish or reach the service’s maximum stream duration — ten minutes here, enforced for exactly this reason. Anything still open at the deadline gets a server_shutdown error event rather than a reset, so clients can retry with a clear conscience. The drain window sets how fast a gateway rollout can go; it is typically the slowest part of shipping the edge.

05 — Inside the gateway

One process, five tables, nothing waits on the network

What is the gateway actually made of?

Every per-request decision in the service is made here, and each one reads a table that something else keeps fresh in the background. The gateway is a small program wrapped around five in-memory tables and one loop per stream.

Envoy + external processing

Mature edge, awkward state

  • TLS, HTTP/2 and connection handling are battle-tested.
  • Per-chunk logic means either an ext_proc gRPC round-trip for every SSE event, or a custom filter in C++, Wasm or a Rust module.
  • Cross-request state — buckets, the stream index, the key cache — has to live outside the proxy or be rebuilt inside a filter.
Purpose-built · recommended

Small program, all state local

  • Go on the standard net/http and HTTP/2 stack, or Rust on hyper. A few thousand lines.
  • Every table is a structure in the same process; the per-chunk path is a function call.
  • The cost is owning edge hardening — kept small by leaving the L4 LB in front and using the language’s stock HTTP stack, not a custom one.

One stream, start to finish

A stream is one handler and one loop. The request context is cancelled the moment the client goes away, and every exit path ends in the same place: cancel the upstream so the engine frees the sequence, release the stream slot.

// one goroutine per request · everything it reads is already in memory
func (g *Gateway) serve(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context()                                  // cancelled on client disconnect
    req, err := g.pipeline.run(r)                       // stages 0–6: limits, key, tokenize, admit, pick
    if err != nil { writeError(w, err); return }        // 401 · 404 · 413 · 429 with Retry-After

    s := g.streams.open(req)                            // stream index + concurrency slot
    defer g.streams.close(s)

    up, err := g.upstream.start(ctx, req)               // h2 stream to a replica; ≤ 1 retry before first byte
    if err != nil { writeError(w, err); return }
    defer up.cancel()                                   // engine aborts; KV blocks freed on its next step

    for ev := range up.events(g.cfg.stallTimeout) {     // parsed SSE from the engine
        if s.revoked.Load() { writeEvent(w, errKeyRevoked); return }
        g.buckets.debit(req.tenant, req.model, OUT, ev.newTokens)   // may go into debt: blocks new admissions, not this stream
        if err := writeEvent(w, ev); err != nil { return }         // client gone or too slow
    }
}

The engine is asked for continuous usage in its stream (vLLM’s continuous_usage_stats), so each event carries an exact token count and the gateway never re-tokenizes output. Output-token limits are debited as tokens pass but never cut a running stream: a bucket in debt refuses the tenant’s next request instead, which is the difference between a limit and a truncated answer.

Backpressure, at both ends

A stream has a producer the gateway doesn’t control and a consumer it doesn’t trust. Each way either can misbehave has a detector and an action.

Retries are rationed. A gateway retries only before the first byte, never on a 4xx, at most once per request, and within a budget of 10% of a pool’s requests over any 10 s. Without the budget, a pool that is slow because it is overloaded gets a retry storm exactly when it can least absorb one.

The catalog is configuration, released like code

Everything the gateway knows about a model comes from one versioned entry. The tokenizer and chat template are part of the model’s revision, released with its weights, because a gateway that tokenizes with one version and a replica that expects another produce wrong answers with no error.

# one catalog entry · shipped as a signed bundle, applied atomically
model:            llama-3.3-70b

Component 2 of 7
Key service

Issues, stores and revokes keys. The gateway asks it only on a cache miss, and otherwise it only pushes — so an outage here is not an outage of inference.

06 — Anatomy of a key

Four fields, four jobs

What should an API key actually look like?

Most of a key’s security properties are decided by its format, before any code runs. A good format lets a scanner find it, a client catch a typo, the gateway reject garbage for free, and the database store nothing worth stealing.

nc_live_PREFIX · 8
k7Qm2xPz9aLr4TbVKEY_ID · 16 · public
_ 43 chars of base62 · 256 bitsSECRET · shown once · never stored
_3fQ1ZxCRC32 · 6
prefix

Say who issued it

Formatnc_live_ or nc_test_. Distinctive enough that a regex over all of GitHub has almost no false positives.
WhyRegistered with secret-scanning programmes, so a key pushed to a public repository is reported to us within minutes and revoked automatically (08).
AlsoTest keys route only to a sandbox pool and can never reach production replicas — the environment is in the key, not in a header someone forgets.
key_id

A public handle

Format16 base62 characters, random. Not secret — it appears in the dashboard, in logs, in support tickets.
WhyThe lookup is by key_id, never by the secret, so the database index is not a timing oracle on the secret and logs can name a key without holding it.
secret

The only secret part

Format256 bits from the OS CSPRNG, base62-encoded to 43 characters.
WhyUnguessable by construction. That entropy is what lets the service use a fast keyed hash instead of a slow password hash (below).
LifecycleDisplayed once at creation. The service stores only its HMAC and can never show it again.
checksum

Reject garbage for free

FormatCRC32 of everything before it, base62, 6 characters.
WhyScanners confirm a match offline; clients catch copy-paste errors; the gateway rejects random strings with no lookup at all. It is not a security control — it is a cost control.

Why HMAC and not bcrypt

Slow password hashes exist to make guessing a low-entropy secret expensive after a database leak. A 256-bit random secret has no dictionary to guess from, so slowness buys nothing — and the service verifies on every request. At 50,000 requests a second, a 100 ms bcrypt check would need about 5,000 cores just to say yes.

Password hash · bcrypt, argon2

Right for humans

  • Protects secrets people chose, which are guessable.
  • Deliberately costs 50–500 ms.
  • Verification is too expensive to do per request, so systems end up caching the plaintext — which is worse.
Keyed hash · HMAC-SHA256 + pepper

Right for machine secrets

  • Stores HMAC(pepper, secret); the pepper lives in a KMS, not the database.
  • About a microsecond to verify.
  • A stolen dump of the keys table cannot be checked offline without the pepper.
  • Each record carries a pepper_ver, so the pepper can be rotated by re-hashing on next use.

07 — Verifying every request

The key service is not on the request path

How do you check a key on every request without asking anyone?

Each gateway keeps its own copy of the keys it has seen. The key service fills it on a miss, pushes changes into it as they happen, and is otherwise never consulted — so an outage there does not become an outage of inference.

Revocation: pushed, with a TTL behind it

A cache that is only refreshed on a timer makes revocation as slow as the timer. So changes are pushed, and the timer exists only to bound the case where a push is missed.

t+0A key is revoked — by its owner, by support, or by the scanner in 08. The key service writes status=revoked and bumps version.
t+50msThe change is published on a fan-out bus that every gateway subscribes to. Each drops its cached entry.
t+100msEach gateway also looks up in-flight streams for that key and ends them with a key_revoked error event. Revocation stops work in flight, not just new requests.
≤ 60 sA gateway that was partitioned from the bus re-fetches every entry older than its TTL. This is the hard worst case, and it only applies to a gateway that is already unhealthy.

Protecting the check itself

An attacker who can’t guess a key can still try to make checking keys expensive. Three cheap layers stop that: a per-IP and per-/24 limiter before authentication, a failed-auth counter that tightens the limiter for sources that keep failing, and the negative cache, which turns repeated forged IDs into memory lookups. None of this touches a GPU — the most a spray can cost is gateway CPU, which is the cheapest thing in the building.

08 — When a key leaks

Decide the blast radius before the leak

What limits the damage when a key ends up on GitHub?

Keys will leak — into repositories, notebooks, mobile apps, and screenshots. The design question is not how to prevent it but how much a leaked key can do before something notices, and the answer should be a limit the customer chose.

1

Secret scanning

The prefix is registered with scanning programmes. A match in a public repository is reported, verified by checksum, and the key is revoked automatically with an email to the owner. This catches the most common leak in minutes, with nobody awake.

2

Scope

Keys belong to a project and can be limited to named models. A leaked key for an internal tool that only calls an 8B model cannot call the 671B one.

3

Per-key quota

A daily and monthly token quota on each key, enforced by the same buckets as the tenant’s limits (09) and separate from them. A tenant with a very large allowance can still say this key may use 20M tokens a day.

4

Network allowlist

Optional CIDR allowlist per key. For server-side keys this makes a leak nearly harmless — the key works only from the customer’s own egress addresses.

5

Velocity anomaly

Each key’s token rate is compared to its own recent history. Ten times its 7-day p99 sustained for five minutes moves the key to throttled — limits drop to baseline, the owner is notified — rather than revoked. Throttling is reversible; a false positive costs the customer latency, not an outage.

6

Revocation

Pushed to every gateway in well under a second, with in-flight streams ended too (07). Rotation is painless because a project can hold several active keys at once.

Replicas trust the gateway, not the key

The customer’s key never leaves the gateway. What travels to the engine is a short-lived context the gateway signs, over an mTLS connection whose client certificate names a gateway workload. The engine verifies the signature and uses the claims for scheduling and usage records — it has no way to authenticate a customer, and no reason to.

# internal request context · Ed25519-signed by the gateway · never seen by the client
{
  "tenant":   "ten_4Kc…",
  "project":  "prj_9Hx…",
  "key_id":   "k7Qm2xPz9aLr4TbV",          # for usage records and audit
  "request":  "req_01J9…",                  # for tracing and abort
  "class":    "interactive",                # or batch — used by the fair queue (13)
  "weight":   4,                            # tier weight in the scheduler

Defence in depth, stated plainly: if an attacker got inside the cluster network they would still need a gateway’s workload certificate to reach a replica, and a gateway’s signing key to make a replica do work on someone else’s account. Neither is on disk; both rotate hourly.

Limit service

Turns each tenant’s limits into a share per gateway, every second. Soft state, no database, and every failure falls back to admitting less.

09 — One limit, many gateways

Shares that follow the traffic

How do twelve gateways enforce one tenant’s limit without asking each other?

A tenant’s limit is one number, but its traffic lands on whichever gateways its connections happen to reach — and with HTTP keep-alive, a tenant with a handful of long-lived connections may be on two gateways out of twelve. The limit service keeps each gateway’s share of every limit in proportion to where the traffic actually is.

Static split · L ÷ G

Local and wrong

  • Every gateway admits one twelfth of the limit. No coordination at all.
  • A tenant pinned to 2 gateways gets 2⁄12 of what it paid for — six times too strict.
  • Still useful as the fallback: it always sums to exactly L.
Central counter · INCR per request

Exact and on the path

  • A Redis round-trip per admission and per chunk — breaking the budget in 02.
  • One hot key per large tenant, on one shard.
  • An outage of the counter is an outage of admission.
# limit service · every second · for each tenant T and dimension d with any recent demand
L       = limit[T][d] / 60                       # per-second rate from a per-minute limit
G       = gateways_alive
demand  = { g: used[g] + denied[g] for g in G }  # what g would have admitted
floor   = 0.05 × L / |G|                         # every gateway can admit a trickle
spread  = L − |G| × floor
share[g]= floor + spread × demand[g] / Σ demand  # Σ share = L exactly
push { T, d, share[g], ver } to each g           # gateway sets bucket rate = share, burst = share × 10 s

Counts, not only rates

Concurrent-stream limits are integers, and a limit of 8 streams can’t be split twelve ways. For these the service hands out whole slots only to gateways with demand, moving a slot when one gateway has queued work and another has a slot idle. Per-key daily quotas (08) are one more dimension, the only one with memory: their running totals are checkpointed every few seconds, so a restart loses seconds of accounting, not a day.

SituationWhat happensWorst case

Why this can be soft state: nothing here is money, and every failure falls back to a split that sums to the limit. The service keeps no database — it rebuilds from two rounds of gateway reports after a restart — and runs as a leader with a warm standby. At 12 gateways and a few thousand active tenants it recomputes on the order of a hundred thousand shares a second, which is arithmetic, not infrastructure.

Router

A library inside the gateway, not a network hop: it picks a replica from live engine metrics and prefix affinity.

10 — Choosing a replica

The least-loaded of two, unless the cache is warm

Which replica should this request go to?

Round-robin assumes every request costs the same, and least-connections assumes every connection does. Neither is true here. The router needs the engine’s own view of its load, and it needs to know where this tenant’s prefix is already cached.

Stale metrics make herds

Engines push queue depth, running sequences and KV use every 100 ms. Every gateway sees the same snapshot, so if a replica looks idle, every gateway sends it the next request, and 100 ms later it is the busiest in the pool. Two corrections: each gateway adds its own in-flight requests to the snapshot, which it knows exactly; and it picks the better of two random candidates rather than the best of all, which is almost as good and doesn’t herd.

# gateway · per request · all inputs already in memory
preferred = ring.lookup(hash(salt_T, first_block(prompt)), bound=1.25 × mean_load)
a, b      = preferred, random_healthy_replica()
score(r)  = queue[r] + inflight_from_me[r]          # snapshot + what I know I just sent
          + α × kv_used[r]                          # near-full KV means preemption soon
          − β × expected_prefix_hit(r, prompt)      # skipped prefill is latency and GPU saved
send to argmin(score(a), score(b))

This is the job the Kubernetes Gateway API Inference Extension calls an endpoint picker, and llm-d and Dynamo ship variants of it. The scoring weights are per pool: an 8B pool with short chats barely benefits from affinity, while a pool serving agent traffic with 20k-token shared system prompts can skip most of its prefill work with it.

11 — Inside one replica

Memory runs out before compute does

What is the scarce resource on a shared replica?

A replica does two very different kinds of work, and the thing they compete for is not FLOPs but the KV cache — gigabytes of per-sequence state that must stay in GPU memory for as long as a stream is alive.

Prefill

Read the prompt

  • All prompt tokens processed in parallel, in one pass.
  • Compute-bound: large matrix multiplies, GPU busy.
  • Writes the prompt’s keys and values into the KV cache.
  • Sets time to first token. A long prompt makes it long.
Decode

Write the answer

  • One token per sequence per step, every sequence in the batch together.
  • Memory-bandwidth-bound: every step reads all the weights and each sequence’s KV cache.
  • Batching is almost free until the KV cache is full.
  • Sets inter-token latency — what streaming feels like.

Continuous batching lets sequences join and leave the batch on every step, so the batch stays full. What limits how full it can get is how many tokens of KV cache fit in memory. The size per token is fixed by the model’s architecture:

Chunked prefill: long prompts can’t freeze the batch

A 100k-token prompt prefilled in one pass stalls every decoding sequence on that replica for the length of the pass — hundreds of milliseconds of frozen streams for everyone else. Chunked prefill splits it into pieces of a few thousand tokens and interleaves them with decode steps, so the long request takes slightly longer and nobody else notices. The chunk size is a direct trade between one tenant’s time to first token and everyone else’s inter-token latency; it is set per pool.

12 — Three layers of isolation

Rate limits are necessary and nowhere near sufficient

How do you stop one tenant making the service slow for everyone else?

A tenant can stay within every request limit and still take over a replica, because requests are not the unit of cost. Isolation needs a layer at the door, a layer in the scheduler, and a layer in memory — each denominated in tokens.

layer 1 · gateway

Limits at the door

LimitsRequests per minute, input tokens per minute, output tokens per minute (counted as the stream runs), concurrent streams — per tenant, per model, per tier.
ImplementationLocal token buckets. Each gateway holds a share of the tenant’s limit; a limit service rebalances the shares every second in proportion to each gateway’s recent traffic for that tenant (09).
StopsFloods, runaway retry loops, a leaked key being hammered.
Doesn’t stopA few enormous requests, or a burst that lands on one replica.
layer 2 · scheduler

A fair queue in the engine

IdeaEach tenant has a counter of service received, in weighted tokens. The next slot in the batch goes to the waiting tenant with the lowest counter per unit of weight — the Virtual Token Counter.
Why tokensCounting requests lets a tenant with 50k-token prompts take fifty times its share while looking fair.
WeightsTier and priority class: interactive over batch, paid tiers over free.
StopsOne tenant’s queue starving everyone else’s at a busy replica.
SpecifiedIn full in 13: where it runs, what it charges, its parameters and its tests.
layer 3 · memory

KV caps and preemption

CapWhile anyone else is waiting, a tenant may hold at most its fair share of KV blocks. When nobody is waiting it can use everything — work-conserving, so the cap costs nothing when idle.
PreemptionWhen memory runs out, evict from the tenant furthest over its share, not from whoever arrived last. Short sequences are recomputed; long ones are swapped to host memory.
StopsThe 128k-token request in 11 taking the replica.
Oversized requestsA request bigger than a fair share still runs — when the queue is clear, or on a larger replica shape. The catalog caps each pool’s context length at what its replicas can hold without starving everyone else.
# the idea in fifteen lines · the full design is section 13
on request from tenant t, when t had nothing waiting:
    counter[t] = max(counter[t], min(counter[u] for u in waiting))   # idle time can’t be banked

while batch has free slots and free KV blocks:
    t = argmin(counter[u] / weight[u] for u in waiting)
    r = next_request(t)
    if others_waiting and kv_used[t] + blocks(r) > fair_share(t):
        skip t this step                                             # layer 3
    admit r

after each step:
    counter[t] += w_in × prefill_tokens[t] + w_out × decode_tokens[t]   # w_out > w_in: decode holds memory longer

The prefix cache is a side channel

Prefix caching keeps the KV blocks of a finished request so the next request with the same beginning skips its prefill. Across tenants that is a timing oracle: if my request for a guessed prompt comes back fast, someone else sent it recently. So every cache key is salted with the tenant — vLLM’s cache_salt exists for exactly this — and hits are only possible within one tenant. The cost is losing shared hits on common public system prompts, which is a small price for not leaking one customer’s prompts to another.

Why all three: layer 1 alone lets a tenant within limits take a replica with a few large requests. Layer 2 alone decides who goes next but not how much memory they hold once admitted. Layer 3 alone protects memory but does nothing about queue order. Each closes the hole the other two leave.

13 — The fair-queue scheduler

A queue in front of the engine, not a fork of it

Exactly how does a replica decide whose request runs next?

vLLM schedules first-come-first-served, optionally by a per-request priority. Neither knows what a tenant is. Fairness is added by an admission queue beside each engine that holds requests back and releases them in fair order — so the engine’s own queue stays nearly empty and its scheduler only ever chooses among requests that are already fair to run.

What a tenant is charged for

The counter measures service in weighted tokens, charged as it is consumed rather than when a request finishes, so a tenant with long streams can’t run ahead unnoticed. The weights say what each kind of token costs the replica.

# added to counter[t] as the work happens
at submission:   W_IN × (prompt_tokens − cached_tokens)  +  W_CACHED × cached_tokens
per streamed token:   W_OUT                              # from the stream the sidecar proxies

W_IN = 1        # prefill: compute-heavy, brief
W_CACHED = 0.1  # a prefix hit costs memory, not compute
W_OUT = 2       # decode: holds KV for the whole stream; tune from measured GPU-seconds per token
# admission queue · one per replica · runs on arrival, on completion, and every 20 ms
state
  q[t]         FIFO of waiting requests for tenant t
  counter[t]   weighted tokens served to t on this replica
  kv[t]        KV blocks held by t’s running requests    # own accounting, reconciled with engine metrics
  heap         waiting tenants, keyed by counter[t] / weight[t]

on_arrival(r):
  t = r.tenant
  if len(q[t]) ≥ MAX_QUEUE: return 429 replica_busy    # gateway retries elsewhere, before first byte
  if t has nothing waiting or running:
      counter[t] = max(counter[t], min(counter[u] for u in heap))   # idle time can’t be banked
  q[t].push(r); heap.update(t); dispatch()

dispatch():
  for t in heap.ascending():                           # lowest counter per weight first
      if engine.waiting > 1: break                     # the engine already has work queued
      r = aged_head() or q[t].head                      # aging bounds tail wait (below)
      need = blocks(r.uncached_prompt + OUT_HEADROOM)
      if kv_free() − need < KV_RESERVE: break
      if others_waiting(t) and kv[t] + need > fair_share(t) and not r.aged: continue
      submit(r, priority = CLASS_PRIORITY[r.class])     # vLLM: lower value runs first, preempted last
      q[t].pop(); kv[t] += need; charge_prompt(t, r); heap.update(t)

fair_share(t) = KV_TOTAL × weight[t] / Σ weight[u]     # over tenants running or waiting here

Requests bigger than a fair share

A 128k-token prompt can need more KV than its tenant’s share even with nothing else running (11). Skipping it forever would starve it; admitting it immediately would evict everyone. Instead it ages: after AGE_MAX it is marked, the gate stops admitting new work from anyone until enough blocks free up, and then it goes in. Streams already running are untouched — the only cost is a pause in new admissions, bounded by how long current sequences take to finish. The same aging applies to any request at the head of a queue, which turns the counter’s fairness into a bounded tail wait per class.

Fair per replica, bounded per pool

Counters are local to each replica. That is deliberately not global fairness: a heavy tenant spread over every replica gets its fair share on each, and a tenant concentrated by prefix affinity (10) looks heavy exactly where it is. The pool-wide ceiling comes from the gateway limits (09). Sharing counters across replicas would put a network round-trip back into the scheduler for a small gain.

14 — What to scale on

Not CPU, and not requests per second

Which signal says a pool needs another replica?

The metric an autoscaler targets should be the thing users feel, or something that moves before it. For a model pool that is time spent waiting in the engine’s queue, and how close the KV cache is to forcing preemptions.

SignalVerdictWhy
GPU utilisationmisleadingNear 100% whenever anything at all is running. It can’t tell a comfortable replica from a drowning one.
requests per secondmisleadingA request can be 50 tokens or 100k. The same RPS can be idle or saturated depending on the mix.
queue wait p95primaryThe part of time to first token that capacity controls (02). Directly tied to the SLO.

pool: llama-3.3-70b
replica_shape: { gpus: 2, type: H100-80G, tp: 2 }

  when:  queue_wait_p95 < 50ms  and  kv_used_p90 < 0.5  for 10m

  drain: stop routing, wait for streams (≤ 10m), then release

Why up is fast and down is slow

Adding a replica costs money for a few minutes. Removing one too early costs a cold start — minutes of degraded latency — the next time traffic rises (15). The asymmetry follows directly: scale up on the first sign of trouble by a fraction of the pool, scale down one replica at a time after ten quiet minutes, and drain rather than kill so streams aren’t cut.

When capacity can’t arrive in time

Demand can outrun even a fast autoscaler. Rather than let queue wait grow for everyone, admission sheds load in order: batch-class traffic first, then free tier, then paid tiers above their committed rate. Shed requests get a 429 with a Retry-After computed from the pool’s current queue estimate, so well-behaved clients back off by the right amount instead of retrying into the storm.

15 — Cold start

A replica takes minutes to exist

Why can’t inference scale like a web tier?

A stateless web pod starts in a second because it is small. A replica has to find a free GPU node, pull a multi-gigabyte image, move tens of gigabytes of weights into GPU memory, and warm up the engine. Almost all of autoscaling design is about skipping some of those steps.

1

Keep GPU nodes warm

A small pool of provisioned, idle GPU nodes per node type, sized to cover one scale-up step for the largest pool. This removes the slowest and least predictable step. It is the most expensive line item in the design and also the one that makes autoscaling work at all.

2

Pre-pull images, pre-stage weights

Engine images are pulled to every GPU node ahead of time. Weights for every catalog model that fits are staged on local NVMe, and refreshed when the catalog changes. Loading then runs at disk speed rather than object-store speed.

3

Sleep instead of scaling to zero

vLLM’s sleep mode moves weights to host memory and frees the GPU, then restores them in seconds. A node can hold a quiet model asleep and a busy one awake, and swap them faster than a new replica could start.

4

Scale on the forecast, not the alarm

Traffic is strongly daily and weekly. A floor from last week’s same hour means the morning ramp is met by replicas that started ten minutes early, not by an alarm that fires at the peak.

Ten pools that share one set of GPUs

How do ten models divide a fixed number of GPUs?

Each model is its own pool with its own autoscaler, but the GPUs underneath are one budget. Something above the pools has to decide which of them gets the next free node, and which gives one back.

Packing, lending, and taking back

An 8-GPU node can hold eight 1-GPU replicas, four TP=2 replicas, two TP=4 replicas, or one TP=8 — tensor-parallel groups must sit inside one node’s NVLink domain. A fleet arbiter above the pool autoscalers owns node assignment. Each pool has a guaranteed minimum and a ceiling. When a pool asks for more and no warm node is free, the arbiter reclaims from the pool with the lowest queue pressure that is above its minimum: stop routing to one of its replicas, let its streams drain, and hand the GPUs over. Draining is what makes lending safe — and it is also why reclaiming capacity is measured in minutes, not seconds.

The long tail

Quiet models are the expensive part of a catalog: two replicas of a model that sees ten requests a minute cost as much as two replicas that are full. Options, in order of preference: keep one awake replica and a second asleep on a node shared with a busier model (15); consolidate quiet 1-GPU models onto fewer nodes; and, if a model stays quiet for a quarter, take it out of the catalog. Scale-to-zero is deliberately not on the list — a first request that waits minutes is not a service anyone would pay for.

Every guarantee in this design has the same shape. A central authority holds the truth, hands out a bounded piece of it to whoever is on the hot path, and takes it back on a timer. The hot path never waits for the authority; the authority never lets the pieces add up to more than it can afford to lose.

It is the same move four times — for rate, for trust, for memory and for capacity — and the design question each time is the same pair: how big is the piece, and what is the worst it can cost if the holder vanishes with it. Choose those two numbers deliberately and write them down, and a shared, public inference service stops being a set of competing concerns and becomes one mechanism applied carefully.

Glossary

Every term the guide leans on more than once. Each also appears as a dotted underline at its first use in a section — hover it there instead of coming here.

bounded load
A consistent-hashing variant where a key goes to its usual node unless that node is over (1 + ε) × the average load, in which case it walks on to the next.
chunked prefill
Splitting a long prompt’s prefill into pieces interleaved with decode steps, so one long prompt doesn’t stall every other stream on the replica.
consistent hashing
Mapping keys and nodes onto a ring so that adding or removing a node only moves the keys next to it.
continuous batching
Scheduling per decode step rather than per request: sequences join and leave the running batch as they arrive and finish.
decode
Generating the answer one token per step. Bound by memory bandwidth; sets inter-token latency.
FP8
8-bit floating point. Halves weight memory relative to bf16 on GPUs that support it, usually at a small quality cost.
HMAC
A keyed hash. Stored for each API key as HMAC(pepper, secret), so a copy of the table can’t be checked without the pepper.
inter-token latency
The gap between successive streamed tokens. What streaming “feels like” after the first token arrives.
KV cache
The keys and values of every token so far, kept in GPU memory so each decode step doesn’t recompute them. The scarce resource on a shared replica.
Little’s law
Items in a system = arrival rate × time each spends in it. 1,500 streams a second × 12 s = 18,000 open.
mTLS
TLS where both sides present certificates. Here, how a replica knows it is talking to a gateway and nothing else.
negative cache
A short-lived record that a key ID does not exist, so forged IDs don’t reach the key service repeatedly.
PagedAttention
vLLM’s technique of storing the KV cache in fixed-size blocks, like virtual-memory pages, so it doesn’t fragment.
pepper
A secret key mixed into every stored hash and kept outside the database, in a KMS.
prefill
Processing the whole prompt in one parallel pass to fill the KV cache. Compute-bound; sets time to first token.
prefix cache
Keeping KV blocks after a request ends so a later request with the same beginning skips that part of its prefill.
single-flight
Collapsing concurrent identical lookups into one: the first caller fetches, the rest wait for its result.
SSE
Server-sent events. A long HTTP response of data: lines — the streaming format of chat completions.
time to first token
From the request arriving to the first streamed token: gateway, queue wait and prefill.
Virtual Token Counter
A fair scheduler that tracks tokens served per tenant and gives the next batch slot to the waiting tenant with the lowest count.
work-conserving
A limit that applies only when someone else is waiting, so an idle resource is never held back.
